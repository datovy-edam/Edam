# ADR-0012 — First-run default project (host policy, not platform behaviour)

- **Status:** **Proposed** — decision required (2026-09-27). Open questions tracked as **D9** in `docs/backlog/Open-Decisions.md`.
- **Context:** The Studio now starts, logs in, resolves its databases and the code editor works — and the project tree is **empty on a fresh installation**. Nothing in the product suggests what to do next, and everything the first run is supposed to demonstrate (open a document, edit it, run a process) needs a project that does not exist yet. Three facts frame the decision, all verified against the current tree: **(1)** the packaged app-data seed ships `Templates` (23 files) and `TextMaps` (8 files) only — `Samples`, `Files`, `Arguments` and `Documents` are **empty**; **(2)** the starter template `Templates/ToAssets.Args.json` reads `./Files/schema.local.v1r0.xsd`, writes `./Documents/referenceData.xlsx` and references `./TextMaps/XsdTextMap.json`, so a project that is created and seeded **today** is structurally complete but **inert** — it cannot run, because no input file exists to seed; **(3)** the Studio has **no delete or remove-project affordance**, so anything created for the user is, from their point of view, a **one-way door**. The platform already provides both halves of the work — `IProjectStore.CreateAsync` (structure, idempotent) and `IProjectSeeder.SeedArgumentsAsync` (content, by address) — and the Studio's own new-project flow already calls both. **ADR-0011** fixes the boundaries that make this a *host* question: locations are addresses, the platform never knows domain vocabulary, and **creating content is a consumer's decision**; **ADR-0010** establishes that the packaged seed is *content to import*, not a location to reach. A container may also be **shared** (LM-4 bindings: a Postgres or service catalog), so writing into "the default container" without looking at where it points would be unacceptable.
- **Decision (proposed):**
  1. **An explicit empty state comes first.** The project tree must say that there are no projects and offer to create one (with a template choice). The application never answers emptiness by silently creating something *as its only response*.
  2. **A gated, one-time default project** may be created **by the host (the Studio)** — and only when **all** of these hold:
     - it has not been created or offered before, recorded by a **once-per-installation marker** (packaged `LocalSettings` or an app-data state file — **never** a catalog item, which would pollute the container);
     - the target container is **empty** (no projects at all);
     - the binding is **local/file-system** (or the container is explicitly allow-listed) — **never** a shared service/PostgreSQL container;
     - the feature is enabled: **`Edam:Projects:CreateDefaultProject`**, proposed default **on for a local binding, off otherwise**.
  3. **Created through the same seams** as any other project (`IProjectStore.CreateAsync` + `IProjectSeeder.SeedArgumentsAsync`) — no special-casing — so the default project is also a live proof that the platform works.
  4. **Idempotent and never resurrecting.** Behaviour is keyed off the marker, **not** off emptiness: a project the user deleted is never recreated.
  5. **Named by configuration** — **`Edam:Projects:DefaultProjectName`** — with a distinct default name; explicitly **not** "Default", which already means the default *data source* in this codebase's vocabulary.
  6. **It reports itself** to the diagnostics panel (created, or skipped **and why**) so the behaviour is never invisible.
  7. **Content ships, it is not invented.** The starter arguments file is seeded by address, and any file it references must either exist in the seed or not be referenced. Concretely: **ship a small sample input in the seed** so the default project can actually run. A project that looks complete and cannot run is worse than no project.
  8. **A way out is a prerequisite.** Project **delete/rename** in the UI (or at least an explicit "this was created for you — remove it" action) must exist **before** any silent creation.
- **Options considered:**
  1. **Create a project whenever none exists** — rejected: it resurrects a project the user deliberately deleted, and on a shared catalog it writes into someone else's container.
  2. **Silent first-run create, ungated** — rejected for the same shared-container reason; the marker alone does not make it safe.
  3. **Explicit empty state only (no auto-create)** — **viable and sufficient**; adopted as the primary UX. The gated default project is an *addition* to it, never a substitute.
  4. **A first-run wizard (choose container → create or skip)** — deferred: more surface and more state for a problem the empty state already solves; revisit if several starter templates appear.
  5. **Ship a starter project as seed content and import it on first run** — **adopted as the content mechanism**: the seed already delivers content (ADR-0010), so the default project's folders *and* its starter arguments *and* its sample input can travel as seed content and be written **by address** (ADR-0011 decision 11). This is how option 2's content is produced without inventing anything at runtime.
  6. **Make the platform scaffold a project automatically** — rejected outright: ADR-0011 keeps scaffolding generic and the domain vocabulary at the consumer level; the platform must not decide that a project should exist.
- **Consequences:**
  - *Positive:* the first run ends in something that works rather than an empty tree; the feature exercises create + seed + tree + editor + runner end to end; the naming and content conventions are taught by example; the work needs **no new platform contract** (both capabilities exist); and the gating keeps shared catalogs untouched.
  - *Cost:* a first-run marker and its lifecycle (upgrade, reinstall, multi-user machines); a config switch and its documentation; a sample input must be added to the seed and kept current; the empty state and the delete affordance are real UI work; and the policy lives in the Studio bridge, so it must be written as *host* policy — not smuggled into the platform.
  - *Neutral:* the default project is an ordinary project; nothing about addresses, containers or the folder set changes.
- **Verification (plan):** a headless **`default project`** conformance group over the existing runner and **both** providers — creates exactly one (structure + seeded starter arguments) when first-run + empty container + local binding + enabled; does nothing (with a distinct reason each) when not first run, when the container already holds a project, when the binding is service/PostgreSQL, or when disabled; never resurrects after a delete; the result is addressable as `/Projects/<name>` and readable through `IProjectResources` with **no path and no CWD**; and the seeded arguments file resolves `./Files/…` **inside the project** per ADR-0011 decision 6. Studio first-run behaviour is user-verified.
- **Open questions (D9):** the default project's name and prefix; whether it is **local-only** (recommended) or allowed for any binding; whether the switch defaults **on** or **off**; whether a sample input is added to the seed; whether delete/rename ships first (recommended); and whether the default project is **created** or merely **offered** (one click, clearly explained).
