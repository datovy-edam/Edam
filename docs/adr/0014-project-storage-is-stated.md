# ADR-0014 — Project storage is a deployment fact, and it is always stated

- **Status:** **Accepted** (2026-10-08) — direction chosen by the user: the catalog binding belongs to the **deployment**, and the database authenticates with **Integrated Security** only. Implements as **Area LM** item **LM-9** (`docs/backlog/LM-9-Storage-Provenance.md`). Builds on **ADR-0009** (projects live in the Catalog), **ADR-0011** (locations and bindings) and **ADR-0013** (unset configuration).
- **Context:** A person using EDAM Studio asked the obvious question — *"where is my project data stored? I expect it in the Catalog, on MS-SQL"* — and the honest answer was that **nobody could tell from the application**, because nothing in it names its storage: the projects were on the **file system** (no catalog connection string was configured) and the only way to find out was to read configuration and code. Three defects of the same family were found in that area while answering:
  1. **A setting stated where the code does not read it.** The shipped `appsettings.json` nests `Edam:Projects:Process` under the `"AppSettings"` object, while the code reads `Edam:Projects:Process` at the **root** (`AppSettings.GetString(key)` reads the key literally) — so the setting is *silently inert*: it looks configured and does nothing.
  2. **A key stated and never handed to its consumer.** `Edam:Projects:DefaultCollection` was read by the Studio's UI preference but **not** passed into the composition root, so the container the store used could differ from the container the UI selected — the same "configured but inert" shape.
  3. **Storage with no provenance.** `ICatalogStore.DescribeStore()`, `ProjectBindingInfo` (`Target`, `Location`, `Credential` **name**) and `ConfigurationItemInfo.Source` already carry everything needed to say *where data is* and *where the value came from*; nothing surfaced it to a person.
  ADR-0013 already separates values by **who owns them** — but it was written for values the app *cannot invent* and the user *must* state. Storage bindings are the opposite: they are **machine/deployment facts**, they carry credentials, and letting a per-user answer shadow what an administrator pinned is a defect, not a feature.
- **Decision:**
  1. **The catalog binding is a deployment fact.** The connection, the storage kind and the container are stated in configuration (deployment/appsettings/environment) and are **not** per-user preferences. The only part a first run may ask for is the **container name**, as a registry item (ADR-0013 decision 2) validated by the container-name rule that also gates project names. A per-user answer may apply only while the item is **unset**, and is **reported as superseded** when configuration later states it.
  2. **Authentication is Integrated Security by default.** No password in `appsettings.json`, in the packaged seed (ADR-0010), in a log, or on a screen. A SQL login is not adopted without a vault; a `vault://` credential remains a host-resolved reference, never a stored secret.
  3. **The storage kind is stated, not inferred.** `Edam:Catalog:Target` names the engine (`filesystem | postgres | mssql | service`). When the configured engine and the connection string disagree, the app **reports the mismatch by name** instead of failing obscurely or silently choosing. (Deriving the engine from a DSN is explicitly *not* adopted; if it ever is, it must be reported as such.)
  4. **The resolved storage is stated at startup.** Target family, storage kind, collection and **redacted** location are reported through the same composition root that resolves them — so it is on the record *before* anything is read or written — and the same values are what the UI renders. *A storage the application never names is a storage the user has to guess at.*
  5. **Redaction has exactly one definition**, applied before a value can be logged or displayed. The UI never redacts, because two rules would eventually disagree.
  6. **A key the application states must reach its consumer.** Configuration is handed to the composition root in full for the keys that matter (`DefaultCollection` included); a key that is inert is either fixed or removed, never left looking meaningful.
  7. **A container is a location the app may create, but a binding it may never rewrite (ADR-0011).** Enlistment is idempotent, and a container's **shared locations** (`Templates`, `TextMaps`, `Samples`) are seeded from the app-data seed **only when missing** (LM-5), so the first project is never inert (DP-4) and a curated template is never overwritten.
  8. **Storage is inspectable from the UI** (LM-9's UI half): the container's info surface names the container, the storage kind, the **redacted** location, whether it is local or remote, and the **source** of the value (configuration · environment · your answer) — never a secret.
- **Options considered:**
  1. **Ask the user for the database location at first run** — rejected: the binding is a machine fact (a shared machine or CI would then disagree with the deployment), it drags credential handling into a UI, and asking a person to choose "MS-SQL or PostgreSQL" is asking them to know our plumbing.
  2. **Infer the engine from the DSN silently** — rejected for now: a heuristic must not decide where data lives; the honest version is to *report* a mismatch, which decision 3 does.
  3. **Keep it in configuration with no UI surface** — rejected: this is precisely how the question above had to be asked in the first place.
  4. **Put the binding in the per-user overlay like other answers** — rejected: credentials would land in a plain per-user file, and the overlay would shadow the deployment (decision 1).
  5. **Deployment-owned binding + startup statement + inspectable container + seeded container** — **adopted**.
- **Consequences:**
  - *Positive:* storage becomes predictable and administrator-controllable; no secret needs to exist for a local installation; "where is my data?" and "where did this value come from?" are answerable from the UI; the class of *configured-but-inert* defects (a key in the wrong place, a key never handed over) becomes **visible** rather than expensive to discover; and switching storage stays a configuration change, as ADR-0007/0009 intend.
  - *Cost:* the deployment must state the binding (there is no longer a silent file-system default when a catalog is configured); a wrong or unreachable binding yields an empty panel — but now with a named reason in the diagnostics panel; the storage description and the redaction rule must be kept current and secret-free; and every new setting must be checked against decision 6.
  - *Neutral:* no contract changes. The platform already exposes `DescribeStore()`, bindings and configuration sources — this ADR is about *stating* and *surfacing* what exists, not about new storage technology.
- **Verification:** build 0 errors across the affected solutions; the storage summary is emitted once, from the composition root, with the location redacted; a stated-but-unread key is corrected or removed; the container is enlisted idempotently and its shared locations are seeded only when missing; and the UI surface renders the same record the diagnostics carry (headless-checkable value record + the user's runtime check).
