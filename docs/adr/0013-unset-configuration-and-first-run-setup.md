# ADR-0013 — Unset configuration: what the app asks the user, when, and where the answer lives

- **Status:** **Accepted** — direction (2026-09-27). **Amended 2026-09-28** (decision 12: an answer is not completion when the item implies an action). Implements as **Area CF** (`docs/backlog/README.md`); first instance is the default project name (**Area DP**, ADR-0012).
- **Context:** The application must resolve some values it cannot invent — where projects live, which organization, what to call the starter project — and the app-data root starts **empty** by design (ADR-0010: the packaged seed is *content to import*, and user state is an overlay). Two hard lessons from this codebase frame the decision. **(1) "Empty" and "unset" are different states, and conflating them caused a real defect:** `AppSettings:AssetConsolePath` is deliberately empty in `appsettings.json`, and code that treated *empty* as *missing* threw at startup; a prompt that fires on "empty" would ask the user about values they deliberately cleared. **(2) Silent fallbacks cost more than they save:** the same period produced a data-source "death trap" where a key resolved nowhere and the failure surfaced deep inside a worker thread. The architecture already states one place per concern — LM-3's settings reader, LM-4's bindings for *machine/collection* storage, ADR-0011's rule that the **host** decides content, not the platform — and the **diagnostics panel** is now wired as the application's audit trail. What is missing is a *pattern* for the remaining class of configuration: values that are legitimately the **user's** to state, that may arrive **later** ("we may find other configurable items"), and that should never be guessed silently. Technically, a WinUI `ContentDialog` needs a `XamlRoot` and the UI thread, so nothing can be asked **during** `OnLaunched` — "on open" means *after the shell is up*.
- **Decision:**
  1. **Configuration has three states, and they are modelled separately: `unset` · `set` (possibly to an empty value) · `invalid`.** Prompts are triggered by **`unset` only**; an empty value that was deliberately set is respected; an invalid value is reported, not silently replaced.
  2. **A registry of configurable items** is the single definition of what can be asked. Each entry declares: **id** · a one-line **"what this is"** explanation · **storage** (file + key) · **policy** · **default** · **validator**.
  3. **Policy is per item, and there are exactly three:** **`silent default`** (never ask — a sane value exists) · **`ask once when unset`** (ask, remember, never ask again) · **`required`** (ask, and the *feature* that needs it stays unavailable until answered — the **application** is never blocked).
  4. **Asking is batched and lazy.** All currently-unset items that need input are resolved in one pass and presented in **one** surface — never a dialog per item, and never a modal storm.
  5. **Two surfaces, one mechanism:** a **first-run setup surface**, shown **after the shell is up** and always **skippable**; and a **lazy ask at first need** (the moment a feature requires the value) for anything discovered later. Content is generated **from the registry**, so no item is hardcoded in the UI.
  6. **Answers are user state, never seed content.** Answers are written to a per-user **app-data overlay** (kept separate from the packaged seed, per ADR-0010). The **once-per-installation marker** (e.g. for ADR-0012's default project) may live in packaged `LocalSettings`. The seed is never written to at runtime.
  7. **Every answer is validated at the point of asking** — an invalid value is never stored. Project names, for instance, must be path-safe: an allow-listed character set, no leading/trailing dot or space, no reserved device names (`CON`, `NUL`, `COM1`…), **no `.` or `..` segments** (a name must not be able to escape `/Projects`), a length cap, and case-insensitive uniqueness within a container.
  8. **Every ask is explainable and recorded.** Each item carries a one-sentence *"what this is"* plus *"what it affects"*; **asked / answered / deferred** are written to the **diagnostics panel**, which is the audit trail for "where did this value come from?".
  9. **Deferring is always allowed.** Skipping or cancelling continues with a **documented** fallback (or leaves the dependent feature unavailable) and records a diagnostic — the user is never trapped in a prompt, and nothing is guessed silently.
  10. **The mechanism is testable by construction.** The decision logic — *what is unset → what to ask → what to write → is the answer valid* — lives **outside the UI** and is proven headlessly, in the same shape as the Area DP conformance sketch.
  11. **`Edam` is the organization.** Names built from it are org-first and dotted, matching the legacy convention (`Datovy.HC.CD`): the starter project is offered as **`Edam.Sample`**, overridable by configuration, and validated by decision 7.
  12. **An answer is not completion when the item implies an action (amended 2026-09-28).** An item may declare a **`CompletedByKey`** — the key that proves its **action** actually happened. Such an item is answered **provisionally**: the value is stored (and the question comes back **pre-filled**, never retyped) but the item **stays in the batch** until that key is stated, because naming something that was never created has achieved nothing. **Validation still outranks a pending action** — a stated-but-unusable value is reported for repair first. The starter project name (decision 11) is therefore `required` with `CompletedByKey = Edam:Projects:DefaultProjectOffered`, so it is asked on **every** run until the project exists.
- **Options considered:**
  1. **Silent defaults only** — rejected: the user never learns or owns the value, and this session shows what an unexplained fallback costs.
  2. **One blocking first-run wizard that asks everything** — rejected: friction, and it fails exactly where values are unknown until later; replaced by decisions 4–5.
  3. **A bespoke dialog per configurable item** — rejected: it does not scale (the user's own observation), duplicates validation and storage, and produces a modal storm.
  4. **Auto-create/auto-fill with a hardcoded value** (e.g. always name the project "Default") — rejected for the same reasons as ADR-0012's option 2, and it collides with existing vocabulary (`Default` is already the default *data source* key).
  5. **Registry + per-item policy + batched ask + user-state overlay** — **adopted**: one mechanism, one audit trail, no hardcoded items, no silent guesses.
  6. **Store the answers in the packaged seed / `Edam.Settings.json`** — rejected: it merges shipped content with user state (ADR-0010), so a later seed copy can fight the user's answer.
  7. **Ask during startup initialisation** — rejected: a WinUI dialog cannot be shown before the window exists; the ask belongs *after* the shell is up (or lazily).
- **Consequences:**
  - *Positive:* the first run ends with the user informed and in control; no hidden fallbacks and no startup traps; **one** mechanism covers every future configurable item instead of a growing pile of special cases; answers are per-user and portable; invalid values are caught where they are entered; and the diagnostics panel answers "where did this value come from?" — which is precisely the question this session kept asking.
  - *Cost:* a registry and its per-item content (id, explanation, policy, default, validator) to write and keep current; a first-run surface; a user-state file with a lifecycle (upgrade, reset, multi-user machines); a policy decision **per item**; and the discipline to keep decision logic out of the UI.
  - *Neutral:* `unset` vs `set` must be modelled once in the settings reader; no new storage technology is required; the platform's contracts do not change (this is host policy over existing seams, as ADR-0011 requires).
- **Verification (plan):** headless checks that `unset`, `set-to-empty` and `invalid` are distinguished and reported distinctly; that an item is asked **once** and never again; that a deferred item continues with its documented fallback plus a diagnostic; that an invalid answer is rejected at the point of asking (including the path-safety rules for names); and that the first-run surface renders the batch **from the registry** rather than from hardcoded UI. The first instance — the default project — is verified by the Area DP conformance sketch.
