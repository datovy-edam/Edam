# ADR-0016 — Settings: one mechanism, two surfaces, three tiers, and an honest "it is applied"

- **Status:** **Accepted** — implemented as **Area ST** (`docs/backlog/ST-1.md` … `ST-5.md`), first increment delivered 2026-10-12. Builds on **ADR-0013** (*accepted*), which defined how the application **asks**; this ADR decides how it **shows and changes** what was asked.
- **Context:** ADR-0013 gave the application one mechanism for values it cannot invent — a registry with per-item policy, a batched ask, a per-user overlay, validation at the point of asking. It did **not** give a place to *review* those values afterwards. What existed instead was an assortment: a first-run `ContentDialog` (`ConfigurationPrompt`) that only appears while something is missing; an editor for the catalog connection string buried inside the **container manager** dialog (`ContainerManagerDialog` + `ProjectServicesHelper.SetCatalogConnectionAsync`); and a diagnostics panel that answers *"where did this value come from?"* one line at a time. Three symptoms followed. **(1) The shell displayed a Settings item that did nothing** — `IsSettingsVisible="True"` with no handler, so the most obvious place a person looks was a dead end. **(2) The same key had two homes** — the connection-string override lived in a dialog about *containers*, which is a different concern; this repository has already paid for duplicate mechanisms twice (LM-3/LM-6/LM-7 record **twelve** duplicated settings copies). **(3) Every surface was one careless step away from a lie.** `UserConfiguration.Effective` layers base configuration + packaged state + the overlay, but **environment overrides are consulted separately** by `ProjectSettings.Read`, so a naive page would show "your value" while `EDAM_ROOT` was in force — the silent fallback ADR-0013 exists to prevent. Equally, writing an answer does **not** rebuild the composition root (`ProjectServicesHelper` caches its provider), so a settings page built on it would look saved and stay **inert**: the exact "configured but inert" defect this area keeps producing. And a third: a binding that **nobody stated** would have been labelled *"the installation's configuration"* — a small untruth with the same shape as the large one.
- **Decision:**
  1. **One mechanism, two surfaces.** The first-run **prompt** is the *ask* surface — policy-driven, batched, at most once per run. The settings **page** is the *browse and edit* surface — user-initiated and revisitable. They share **one** catalog, **one** editor, **one** validator and **one** store; neither may grow its own. ADR-0013 decision 5 said "two surfaces, one mechanism"; this is the second surface.
  2. **The settings vocabulary is a dependency-free contract** (`Edam.Settings.Contracts`): a read model (`ISettingsCatalog`, `SettingsItemInfo`) and a write model (`ISettingsEditor`, `ISettingsApplier`). It names no UI, no storage technology, no provider and no project type, so **a WinUI page, an HTTP endpoint, a CLI and an MCP tool render the same answer**. Behavior (`SettingsService`) lives beside the contract in `Edam.Settings.Core`; each module supplies its own catalog/editor (the projects module does, in `ProjectSettingsCatalog` / `ProjectSettingsEditor`).
  3. **A surface is generated, never hardcoded.** A setting is added by extending the **registry** (`ConfigurableItemInfo`: `Group` · `Kind` · `Tier` · `ApplyScope` · `Choices`), so a new setting is a registry entry rather than a XAML edit. This is ADR-0013 decision 5 applied to a page: no item may be hardcoded in the UI.
  4. **Three tiers, kept visibly apart.** **Your values** (editable, overlay-backed) · **Set for this installation** (a deployment/environment fact — read-only *here*, and saying so) · **Recorded state** (evidence that an action happened; read-only, under *Advanced*, explained as *not a preference*). Mixing them is what makes a settings screen untrustworthy.
  5. **Provenance is honest, including when the answer is "nobody".** Every value names the layer that stated it — *your value · recorded for this installation · the installation's configuration · an environment variable · the documented default · not set* — and **the environment wins**, as it does everywhere else (LM-4). A binding nobody stated is reported as the **documented default**, never as deployment.
  6. **Editability is honest too.** An **action-backed** value is editable only while its action is **pending**: once the starter project exists, the name that created it is no longer in play, so offering to change it would promise something nothing reads. Installation facts are never editable from the page; the reason is shown instead of a disabled box with no explanation.
  7. **"Saved" and "applied" are different claims.** Each item declares `ApplyScope` (*immediate · next use · restart*), and the host supplies an `ISettingsApplier`. Only an **immediate** item is applied, through the host's own hook; a value that was stored but **could not** be applied is reported as *stored, but it did not take effect* — never printed as success.
  8. **Reset respects ownership.** *Reset* one value is offered only when the value is the person's, and *forget my answers* clears the overlay only — the once-per-installation markers are spared, so a deleted starter project is never resurrected (ADR-0012 decision 4).
  9. **One write path per key.** The container manager's connection-string editor and `SetCatalogConnectionAsync` are **retired**: the dialog now *states* the catalog's storage and points to Settings → Catalog. Two editors for one value is the duplicate-mechanism defect this repository keeps re-learning.
  10. **The Arguments domain is stated as a default, in two items.** `Edam:Arguments:Domain:DomainId` and `…:Description`, because the per-user overlay stores key/value pairs and each field keeps its own validator. The **shipped starter arguments now state that domain**, so a project created by the default-project flow (DP-4) no longer produces a `domain-missing` warning from the application's own validator. Per-project domains remain per-project: this is the **default a new document is written with**, not a global reassignment.
  11. **Writes over the network wait for an identity.** The Wave-1 API exposes the catalog **read-only** (`GET /settings`, `GET /settings/{id}`); settings *writes* are exercised through the **CLI** and the **desktop**, both of which have a person behind them. An unauthenticated write endpoint would let any reachable client rewrite the deployment's answers; that is a tracked follow-up (ST-4), not a hole opened today.
  12. **The first increment surfaces; it does not invent preferences.** Theme, diagnostics verbosity and panel-on-start are **not** in v1: each is new behavior rather than a view of existing configuration, and the platform is proven first (ST-5).
- **Options considered:**
  1. **Extend `ConfigurationPrompt` into the settings editor** — rejected: a prompt is a *work queue* ("what must I ask now?"), not a *catalog* ("what can I see and change?"); it is modal, it is user-verified as-is, and a page must show items that are not askable and items that are not editable at all.
  2. **A separate settings window** — rejected: unusual for WinUI, and it adds window/lifecycle wiring for no benefit over the frame the shell already has.
  3. **A bespoke XAML row per setting** — rejected: it re-introduces the hardcoded-item problem ADR-0013 decision 5 exists to prevent, and makes the surface drift from the registry.
  4. **Build the catalog inside the WinUI project** — rejected: it would make the feature WinUI-shaped, which is exactly what "UI-agnostic" forbids; the contract must be reachable by a web host, a CLI and an MCP tool.
  5. **Show the effective value only, without provenance** — rejected: it is the silent fallback wearing a friendlier face; the person cannot tell whether the value is theirs, the deployment's, or an environment variable's.
  6. **Contract + service + registry-driven catalog, three tiers, declared apply scope** — **adopted**.
- **Consequences:**
  - *Positive:* the dead Settings item becomes the obvious place to review and change the values the application cannot invent; **one** mechanism now covers asking *and* reviewing, so a future configurable item is a registry entry; provenance makes "where did this come from?" answerable without reading the diagnostics panel; "saved" no longer silently means "inert"; and the same catalog is served by a UI, an API and a CLI, so the three cannot drift.
  - *Cost:* two new projects (`Edam.Settings.Contracts`, `Edam.Settings.Core`); a per-item decision (**group · kind · tier · apply scope**) every time an item is added, and the discipline to keep a surface from growing its own store or validator; a host-supplied applier where a change has a real effect; and an ongoing obligation to keep provenance accurate (the `Environment` and `Documented default` cases are the ones that go wrong quietly).
  - *Neutral:* no new storage technology (the overlay and the packaged marker are ADR-0013's); no change to the project platform's contracts; the WinUI page renders the catalog imperatively, in the same style as `ConfigurationPrompt` and `ContainerManagerDialog`, so it needs no new XAML plumbing.
- **Verification:** headless, in the projects conformance runner, driving the **same** service a surface drives — **`settings catalog (ST-1)` 8 checks**, **`settings provenance (ST-2)` 6 checks**, **`settings apply (ST-3)` 9 checks**, all **ALL CONFORM**, alongside the untouched CF-1 (15), CF-2 (17) and CF-3 (14) groups. They prove: every applicable registry item appears exactly once with a section and an explanation; sections follow the contract's order; deployment facts and recorded state are read-only and say why; an item that does not apply is absent; an action-backed value is editable while pending and not afterwards; a value names its source and **environment wins**; an unstated binding reports *default*, not *deployment*; an unusable stored value is reported and never replaced; one editor is the only write path; validation precedes storage; installation facts and completed actions are refused with reasons; an immediate change invokes the host hook while a next-use change does not; a save that did not apply is reported as such; reset restores inherited values and spares markers. **Delivered builds:** `Edam.Data.Projects.slnx` 0 errors; `Edam.slnx` (WebApi + CLI) 0 errors; `Edam.WinUI.Controls.csproj` (x64) 0 errors; full `Edam.Studio.sln` recorded in `docs/HANDOFF.md`. **Pending (user-side, F5):** that the gear opens the page, that a save is reflected immediately, and that the connection override still rebuilds the storage from the page.
